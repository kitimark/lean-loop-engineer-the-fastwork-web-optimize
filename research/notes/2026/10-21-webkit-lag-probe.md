# WebKit lag probe (2026-10-21)

Question: in the two regions where Safari lags, which counters and which parts carry the work, and how does the
faithful rewrite (default preset, no flags) compare with the original? Region **A** is the hero cards moving out:
zone 0 of `y`, that is `y < vh`. Region **B** is the end of the page: zone 0 of `maxY - y` (not already A), plus the
nav morph that a wheel push at the end of the page opens and closes. **Calm** is zone 2 or more from both ends. The
regions are `Fw.Measure.WebKitLag.regionOf`, defined through `Fw.Measure.WebKit.zoneIx` (`regionOf_a_iff_zone`,
`regionOf_b_iff_zone`, `regionOf_calm`).

**Unit of decision.** A ranked attribution of the Simulator lag, per region and per part, by a unit-free statistic.
An arm difference is stated only when the per-pass ranges of the two arms do not overlap (Lean `verdict`). Otherwise
the text says "no difference shown (ranges overlap)".

**Accepted limits.** Simulator WebKit (iOS 27.0, 430x775 CSS px, DPR 3), not a phone. No candidate fix here. Duration
columns (`us`) are Simulator-host microseconds and are never phone time.

## Measured

- Every number in the block below is generated by that command; nothing in it is typed by hand. The block is replaced, not edited.
- **Ranking.** A counter's key is the ratio `(window sum / window frames) / (baseline sum / baseline frames)`. It has no unit, so counting a column in a unit k times finer, k a positive integer, cannot change the order: Lean `ratio_scale`, `rankWindows_scaleCol`. Raw excess does change it (`excess_flips`); the round 1 note ranked by excess and put paint area first because of its unit.
- **Per-pass range.** Each pass is ranked against its own baseline; the range is over the passes of an arm (6 passes, 3 jobs). The "difference" columns are `verdict` on those ranges, once for the ratio and once for the per-step or per-frame value (a ratio can differ only because the two arms have different calm baselines, for example Layout us).
- **Morph baselines.** The morph rows are ranked against the scroll calm baseline per frame (calm steps of the same pass divided by 2 frames per step). The 10 frames before the push (nothing moving, the page tail) are a second baseline, shown as "idle page tail"; it is not calm.

## Method

- Lane: `packages/measure-webkit/src/lag/` (probe `probe.mjs`, join and format `report.mjs`, reductions `reduce.mjs`, note filler `note.mjs`, CLI `cli.mjs`). Timeline records are cut into steps by `performance.mark('wk:s<k>')`. Scroll run = the lane's stepped scroll. Morph run at the end of the page: 10 idle frames, a synthetic `WheelEvent` (delta +120) on `document.body`, 60 frames, a `WheelEvent` of -120, 60 frames, one rAF per step mark.
- The morph is real: the nav box grows to the full viewport during the open push and shrinks back in the close push (block: "nav box differs from the idle tail in N frames"). The page does not call `window.scrollTo` for it (0 calls), `--morph` reads 0 before and after because it is sampled after the close.
- Paint attribution: a Paint record is joined to the smallest part box covering at least half of its clip (`owner_smallest`, `owner_covers`); leaf parts roll up to the name before the first `-`. Boxes come from an untimed geometry pass (`getBoundingClientRect` at every scroll step; for the morph, a second pass with the same frame schedule). **INFERRED**: the geometry pass is another load, so morph frame k of the sampling pass is not the timed frame k. A timed step takes the boxes of the geometry step with the nearest y (the page is 36 px shorter in some loads, in both arms).
- Paint quads are in document coordinates on iOS: `contentsToRootView` goes through `ScrollView::contentsToView`, which returns the point unchanged when the native view scrolls (ScrollView.cpp:989-993@862f17dcae0a). **MEASURED** in a local debug run (not a result): the clips stayed in document coordinates while the boxes moved with the scroll.
- Why not the node id: `PageTimelineAgent::didPaint` adds `nodeId` only when `nodeIdForRenderer` finds a persistent DOM agent id (PageTimelineAgent.cpp:285-310@862f17dcae0a); with no DOM agent attached it is absent (follow-up 1).
- Forced exit of the lag session (`PipeWrap open`). **MEASURED** in the logs, **INFERRED** cause: the open handle is ours (proxy child pipes of `startProxy`); harmless, watchdog exits 0 after 20 s; not fixed here (follow-up 10). The same line is in older determinism sessions. The probe writes `<vm>-lag.json` before it, so the workflow `lag-report` job now runs when at least one lag JSON per arm exists (`!cancelled()`, `needs.sim.result != 'cancelled'`). One verifying dispatch is still to do (handoff, open item 1).
