## Finding: the WAAPI start leads the rAF start by less than one frame (negative result)

- Two touch rows are model-bugs (MEASURED, runs 39312308173 and 39312313059):
  - Paint `=o`: the sums are near (2757/2761/2757 against 2757/2755/2755). The per-frame counts differ at frames 498-499, 506-508 and 528, and at 506-508 the arm's counts are the base's counts one frame earlier.
  - compositeFailedBits `<o`: the total holds (rewrite 2085664 against waapi 2151424). The frames are not pointwise ordered: frame 498 is 0 against 57440, frames 499-500 are 24576 against 41024, and frame 501 is 24576 against 0.
- Mechanism (CONFIRMED in Blink, INFERRED as the cause of the shift):
  - The original tween starts at the handler's `performance.now()`.
  - The variant sets `startTime = document.timeline.currentTime`.
  - Inside a frame, that time holds the frame time (third_party/blink/renderer/core/animation/animation_clock.cc:58-59@f842f52, set in core/page/page_animator.cc:84-99).
  - Outside a frame, the read is snapped back onto a 1/60 s grid that starts at the last frame time (animation_clock.cc:71-85).
  - Either way the start read lies at or before the push time, and the lag varies from push to push. Premise R5 `start_eq : startRead n = n + c` assumes one constant offset, so it does not hold in Chromium.
- Lean:
  - `start_eq_refuted`: a start read that equals the push time once and lags it once fits no constant `c`.
  - `lead_within_frame`: a lead `δ` with `0 < δ < p` puts the variant's elapsed time strictly between the original's at the same frame and at the next one. Progress is monotone in elapsed time, so a threshold crossing can only move to the same frame or one frame earlier. That bound matches the measured one-frame shift.
- Lesson: an equal-total prediction on a deterministic class is judged frame by frame. A clock source change that is correct in total still breaks a `=o` or pointwise `<o` row. To compare clocks, both arms must read the same clock. Otherwise the row needs a totals-only judgement.

## Accepted limits

- The touch tail is 30 frames, which is shorter than the 680 ms tween, so the measured saving of 33 per run is a lower bound for one tween (INFERRED).
- No frame-498 quarantine was used.

## Open

- The touch Paint `=o` and compositeFailedBits `<o` rows need a redesign. One option is to start the variant from the handler's time, by converting `performance.now()` to timeline time. The other is a totals-only judgement for these rows.
- morph-layers: `waapi.golden.test.ts` could also read `morph-tween-waapi.swipe-v1.jsonl` and pin the swipe rows to `=o`.
- Premise R5 in `WaapiPremises` should carry the frame-grid start read in place of `start_eq`. `pred_sound` then needs a bound of one frame instead of equality.
