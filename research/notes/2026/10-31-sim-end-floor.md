# sim-end-floor: does the iOS Simulator page pay a style recalc per frame at the end of the page, and which flag carries it

Task `sim-end-floor`, follow-up of `10-30-scrolldriven-park.md`. WKTR (threaded-animations pref OFF) read a `shared` floor of 1 recalc per frame
at the end of the page: each of `hero.exit:threaded` and `engine.scroll:unthrottle` alone held it. This note asks the same on the CI iOS
Simulator, through Web Inspector Timeline records. No flag or preset change.

## 1. Runtime and threading status

- MEASURED (`results/sim-end-floor/r1/verdict.txt:2`): runtime `com.apple.CoreSimulator.SimRuntime.iOS-27-0` (iOS 27.0, build 24A434, CI runner
  `results/sim-end-floor/r1/tools-facts.txt`, run 41135293682), page UA `Version/27.0` (the UA keeps `iPhone OS 18_7`, a frozen OS token).
- CONFIRMED from source (WebKit@862f17d): the preference `ThreadedScrollDrivenAnimationsEnabled` is stable and defaults to true for WebKit and
  WebCore under `ENABLE(THREADED_ANIMATIONS)` (`Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml:8518-8531`); a keyframe effect on a
  progress-based timeline can then have an accelerated representation (`Source/WebCore/animation/KeyframeEffect.cpp:3253-3259`).
  `ThreadedTimeBasedAnimationsEnabled` is a preview preference, default false.
- INFERRED: the Simulator's WebKit has the scroll-driven preference ON (source default, no override read). The harness did not read the preference at
  run time, so "ON" is the source default, not a measurement. WKTR ran with it OFF, so the two runs differ in this preference and in the engine
  build (WKTR is not iOS Safari).

## 2. Per-arm rate (MEASURED)

`Fw.Device.SimEndFloor`, band `band = 10` per 100 frames, fixed before the data; window 360 `requestAnimationFrame` callbacks, 3 rounds, arm order
rotated per round, one CI job, run 41135293682, 1847 s).

| end of page, idle (rounds 1 to 3) | 200, 200, 200 | 200, 200, 200 | 200, 202, 197 | 204, 203, 200 |
| back at the end after one viewport up and down | 200, 200, 200 | 200, 200, 200 | 200, 200, 202 | 200, 200, 200 |

Recalcs per 100 frames (`results/sim-end-floor/r1/verdict.txt:3-5, 10-12, 17-19`).

- The base page, with no flag, reads 200 recalcs per 100 frames in all 3 rounds at the end of the page, so removing a flag from the preset cannot cut a
  floor that the base already pays.
- Verdict per flag (Lean `flagV`, `baseFloor`): `hero.exit:threaded` baseFloor and `engine.scroll:unthrottle` baseFloor, in 3 of 3 rounds and
  overall (`results/sim-end-floor/r1/verdict.txt:6-8`). Pair verdict `baseFloor`. Neither flag is shown to carry the floor on the Simulator, and neither
  is cleared: the unit the verdict reads is the cut against the base, and the base has none to give.
- Frame counts: `seen` (FireAnimationFrame records) equals 360 in 32 of 36 windows; the other 4 read 362 to 375 (`results/sim-end-floor/r1/rows.txt`),
  all at least the minimum of 288, so no window is unreadable and no Timeline record loss shows. `RenderingFrame` records read 0 in every window
  (rows.txt, `renderingFrame 0`), so the frame count is the animation-frame record, not the rendering frame.
- The windows are slow: 360 frames span about 9 to 21 s in the end window (`rows.txt`, `span`), about 26 to 59 ms a frame, so the Simulator renders at
  about 17 to 39 frames a second. Rates are per frame, never per time.
- One attempt failed (round 3, base: `Runtime.evaluate timed out after 120000 ms`, see `results/sim-end-floor/r1/sim-log.txt:14`).
  The attempt was retried from a fresh load after a reconnect; the retried window is the one reported.

## 3. What the rows show beyond the verdict

MEASURED, run 41135293682, in `results/sim-end-floor/r1/rows.txt` (rows `round 1 paused ...` and the `census` lines), reading INFERRED.

- Every rendered frame in the base end window carries 2 style recalcs and about 1 layout, 4 paints and 1 composite (rows `round 1 end base`: recalcs 723, layout 415,
  paint 1445, composite 360, schedule 360 over 360 frames). With all animations paused the base drops to 1 recalc per frame and 0 scheduled
  recalcs (row `round 1 paused base`: recalcs 360, schedule 0), and the v2p, minus-threaded and minus-unthrottle arms keep 2 recalcs and 360 scheduled
  per 360 frames when paused (rows `round 1 paused v2p`, `minusT`, `minusU`). All 3 rounds agree (rates in section 2).
- The census lines say what was running: base 8 running document animations at the end (3 accent idle, 1 cue float, 4 platform sweep), v2p 5 (accent idle
  is paused by `platform:faded-pause`), plus 13 finished view-timeline animations (`hero.exit:threaded`) and 1 finished scroll-timeline animation
  (`engine.scroll:unthrottle`) in the arms that carry the flags; paused, no animation is running (`running []`).
- INFERRED: the floor of 1 recalc per frame that survives in the base with everything paused is not a flag effect and not an animation effect. Whether
  it comes from the page's own per-frame work or from the Timeline recording itself is not separated by this run. The scheduled-recalc column (0 in
  the paused base, 360 in each paused flag arm, including the two arms that keep only one flag) fits the WKTR `shared` split (each flag alone holds
  the second recalc), but the Lean verdict does not read it: the base is already above the band, so the verdict is `baseFloor`.

## 4. Against WKTR

- The Lean comparison against the WKTR pair `sharedOrOther` reads `different` in 3 of 3 rounds and overall, for all three stages
  (`results/sim-end-floor/r1/verdict.txt:9, 16, 23`).
- Why different (INFERRED, per the threaded flag): in WKTR the pref was OFF, the base read 0 and each flag alone held 100 per 100. On the Simulator the
  base reads 200, so there is nothing for a flag to carry. The scroll-driven pref is ON by source default here, so the 13 view-timeline and 1
  scroll-timeline animations qualify for an accelerated representation; if they stopped ticking on the main thread the flag arms would read below the
  base. They read the same as the base, so on this run the threaded preference does not lower the page's recalc rate. This does not show the
  animations are accelerated: no probe of the accelerated state was recorded.
- Instrument caveat: WKTR counted the engine's own rendering-update counter with no recording; here the count is the Timeline's `RecalculateStyles`
  records while the Timeline is recording. A recording that forces style or layout each frame would raise every arm equally and give exactly
  `baseFloor`. This is the one reading of the data that this run cannot exclude (follow-up below).

## 5. What it means for the phone session

- The Simulator Timeline cannot rank the two flags by recalc count: it reads 200 per 100 frames at the end of the page for the base and the flag arms
  alike, so a phone comparison of the arms by felt smoothness or by engine events is not predicted to separate on a recalc count here.
- The phone session still decides felt smoothness; this note adds no claim about it. The Simulator on a CI VM is not the phone (17 to 39
  frames a second in these windows).
- Next step (follow-up, not done): a control that keeps the recording and removes the page content (blank body, no animations), to separate the
  instrument's per-frame cost from the page's; then re-read the flag split on the page only if the control reads 0.

## 6. Method and stand-ins

- Lean decision `lean/Fw/Device/SimEndFloor.lean`; golden `packages/contracts/golden/device/sim-end-floor.jsonl`; the TS verdicts
  (`packages/measure-webkit/src/sim-end-floor.mjs`) equal the golden in `test/sim-end-floor.test.mjs`. Listed TS stand-ins with no Lean proof: `windowOf`
  (counts Timeline rows between two page marks), the page script `endFloorJs` and the run loop (`sim-end-floor-run.mjs`), which are recording glue.
- Harness limits: one local debug run (not a result, not reported) found the arm search must be in the reload and that `RenderingFrame` reads 0 on this
  runtime; the CI run above is the only reported run. The census and the paused stage were added after that run to explain the base floor.
