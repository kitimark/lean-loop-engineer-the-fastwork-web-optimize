# Agent state from the real transcripts

**Question (user, 2026-10-18):** can the team's tooling tell what each agent is doing from the real chat logs in the session's
`subagents/` directory, instead of guessing from timers? **Answer: yes.** Three read-only researchers (workflow
`transcript-signals`) surveyed 376 agent transcript/meta pairs and 37 workflow journals, and rebuilt the timelines of 8 agents
from the files alone.

## The rule (from part B; it reproduces 7 of 8 agents, and the 8th mismatch is real)

- `BG(A,t)`: every `toolUseResult.backgroundTaskId` in A's transcript up to t (for workflow agents, the text
  `Command running in background with ID: <id>` on a Bash tool_result), plus child agent ids from `Agent` results.
- `END(b,t)`: a `<task-notification>` for b up to t, in A's transcript (a `queued_command` attachment or a wake record), or in a
  lead queue-operation. Alternatively, the last line of `<tasks>/<b>.output` is `[exited with code N]` or `[killed]`.
- `PEND = BG − END`. `HB`: a SubagentHandback tool_result with `toolEndsTurn: true`.
- The turn is open if the last boundary is a START (first record, or a user record with a top-level `origin`). It is closed
  on `stop_reason: end_turn` or `toolEndsTurn`.
- State: open turn → **working**. Closed turn, then:

  | PEND | HB | Lead notice | State |
  |---|---|---|---|
  | ≠ ∅ | no | | **waiting-on-own-background**(PEND) |
  | ≠ ∅ | yes | | **handed-back-held**(PEND) |
  | = ∅ | | 'finished' | **finished** |
  | = ∅ | yes | | **handed-back-done** |
  | = ∅ | no | | **idle-after-turn** |

- `meta.finished` means "not running right now", not "done". It is set at every stop of a background agent, including a stop
  that leaves background shells running, and removed on resume. It is never set for workflow agents or teammates.

## What this found that the lead had missed
- port-nav's background task (a `cat > file` waiting on stdin, auto-backgrounded at 00:54) was still alive more than 3 h later.
  The lead killed it by PID at about 04:2x. No file signals a task that hangs silently: catching one needs `ps` matched to the
  tool_use command text.
- PID 65901 (the 'merge (playwright-webkit) completed' loop) belonged to port-platform, not integrate-ports. The incident
  ledger has been corrected.
- When an agent's only live child is another agent, its stop sends the lead no notice at all.

## Collector gaps (part C), handed to the next-action work
1. Retention uses `meta.finished` as "ended" and drops the agent after 1 h, even with an unlanded branch.
2. A stale `finished` on a resumed agent.
3. Workflow agents' background tasks are missed (their transcripts have no `toolUseResult`).
4. `next.ts` reads branches only from `git worktree list`; use `meta.worktreeBranch` instead (7 unlanded branches have no worktree).
5. The `[killed]` end marker is not recognised.
6. Loops on agent-transcript outputs have no end marker; use `meta.finished`, the lead notification or the journal result.

- Inventory: 376 meta+jsonl pairs (195 lead children incl. depth 2, 23 teammates, 158 workflow agents in 37 workflow dirs), plus 37 journal.jsonl files. 413 jsonl in total. Agent record types: user, assistant, attachment, system/compact_boundary, api-request, api-request-blob, api-request-shape. The lead file adds mode, permission-mode, last-prompt, ai-title, queue-operation, frame-link, bridge-session, atis-latch, system/turn_duration and system/stop_hook_summary.
- Answer to the 'finished' question: meta.finished=true is written at every stop of a background agent, including a stop that leaves background bash running. It is deleted when the agent is resumed. It is never set for workflow agents or teammates. So finished means 'not running right now', not 'done'.
- No meta or subagent-transcript field records 'waiting'. The only explicit marker is in the lead transcript: the summary 'is waiting on its own background work', and then only for live bash children. To get waiting state for all agents, derive it from the agent jsonl: backgroundTaskId values and async Agent agentIds launched, minus task-ids that came back in task-notifications, checked at each turn end. 81 turn ends in 95 files had live children.
- When a subagent's only live child is another agent, its stop notifies the lead of nothing (no WAITING, no finished). The child's hand-back wakes it later. A detector that relies on lead notifications alone will see these agents as silently running.
- TaskStop and workflow kills leave no marker in the stopped agent's jsonl. The exception is workflow kills, which write '[Request interrupted by user]'. The lead sees the stop in the TaskStop toolUseResult, and in the workflow json status 'killed' plus journal 'started' records that have no 'result'.
- <tasks>/<id>.output files are symlinks to subagents/agent-<id>.jsonl for agents (197 symlinks) and plain files for shell logs (391). A notification's <output-file> therefore points at the transcript itself. Scratch scripts for this survey are under <session-scratch>/transcript-signals/schema-survey/.

- RULE part 1 (sets): BG(A,t) = every toolUseResult.backgroundTaskId in A's jsonl at or before t, plus child-agent ids from Agent results. END(b,t) = any <\task-notification><task-id>b at or before t, in A's jsonl (queued_command or origin wake) or in a lead queue-operation enqueue. PEND = BG minus END. HB = a SubagentHandback tool_result with toolEndsTurn:true at or before t.
- RULE part 2 (turn): turn START = the first record, or a user record with a top-level origin (task-notification, coordinator or peer). Turn END = assistant stop_reason end_turn, or toolEndsTurn:true. The turn is open if the last boundary at or before t is a START. queued_command attachments and compaction are mid-turn.

Closed turn: PEND not empty and no HB -> waiting-on-own-background(PEND); PEND not empty and HB -> handed-back-held(PEND); PEND empty and the latest lead agent notification says 'finished' -> finished; PEND empty and HB -> handed-back-done; otherwise idle-after-turn.
