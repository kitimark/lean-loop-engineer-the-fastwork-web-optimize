# Chromium window reader: a minimum frame count per window

Tags: MEASURED (CI run id named), CONFIRMED (Lean theorem or source cited), INFERRED (reasoned, not seen).

## Answer

* Each window now has a minimum frame count `minFrames` (`lean/Fw/Measure/OffscreenWindows.lean:553-568`). A window
  whose common frame count (`commonLen`, the shortest window over every run of both arms) is below it reads `noData`
  (`minVerdicts`, line 572). Above it the verdict is the own-end verdict of `ownVerdicts`, unchanged.
* A run shorter than `minFrames` in a window makes that window `noData` for the arm pair. The run is not dropped.
  CONFIRMED by `minVerdicts_short_noData` (line 626). The reason is the counterexample below: dropping a short run can
  turn a `noGain` into a `gain`.
* morph.stage re-read (runs 40339630528 base, 40339622735 flag, MEASURED from their counts.json, no new CI run): end
  0-19 now reads `noData` (3 frames, minimum 20), where the own-end rule read `gain`. The approach stays `noGain` on 34
  frames. Finish moves from `noGain` on 37 frames to `noData` (minimum 174). No window of the stage run gives a gain.

## The minimum per window (CONFIRMED, `minFrames_eq`, `minFrames_push`, `minFrames_finish`, `minEnd120_eq_end0`)

`minFrames n` is the length of window `n` in `wholeWindows`, the windows of a run that ends at frame `approachFrames`
and records `120 + minEnd120` frames after its end, so nothing is clipped.

| window | minFrames | reason |
|---|---|---|
| approach | 34 | its whole span (`approachFrames`); a shorter approach means the run ended before frame 34 |
| end 0-19 | 20 | its whole span |
| end 20-59 | 40 | its whole span |
| end 60-119 | 60 | its whole span |
| end 120+ | 20 | no fixed span; `minEnd120`, the span of end 0-19, the shortest fixed end window |
| finish | 174 | the sum of the five push windows at their minimum (`pushWindows_sum`) |

A fixed window is thus compared only whole. The `commonLen` cut still applies to end 120+ and finish when every run
holds at least the minimum.

## Theorems (CONFIRMED, `lean/Fw/Measure/OffscreenWindows.lean`)

| statement | theorem |
|---|---|
| a gain or a noGain in window `n` needs `minFrames n <= commonLen` | `minVerdicts_needs_frames` |
| a run with fewer than `minFrames n` frames in window `n`: the window is noData | `minVerdicts_short_noData` |
| the same run never yields a gain in that window | `minVerdicts_short_not_gain` |
| each verdict is the own-end verdict or noData | `minVerdicts_eq_or_noData` |
| a gain is also a gain under the own-end rule | `minVerdicts_gain_own` |
| every run at or above `minFrames` in every window: the verdicts are `ownVerdicts` | `minVerdicts_eq_own` |

`minVerdicts_eq_own` also covers the case with no valid run: both rules then read noData (`ownVerdicts_noData_of_fewBase`).

## Why a short run is not dropped (CONFIRMED, `#guard`s in `OffscreenWindowsGolden.lean:225-227`)

`dropVerdicts` (`OffscreenWindowsGolden.lean:156-160`) is the rejected rule: per window, drop the runs below
`minFrames`, then judge the rest with `ownVerdicts` (`minRuns` still applies). Case `dropBase` against `dropFlag`: 4
base runs, one of them 50 frames shorter (10 frames in end 120+) with no raster tasks; the flag has no raster tasks
after frame 100. In end 120+:

| rule | verdict |
|---|---|
| own-end (all runs cut to 10 frames) | noGain: the short base run's raster count 0 overlaps the flag's |
| drop the short run | gain: the 3 remaining base runs all raster more than the flag |
| minFrames (this note) | noData |

Dropping picks which runs count after seeing their lengths, and the run it removes can be the one that disagrees. The
noData rule decides each window on every run it has.

## Revision after profile-end-tail

profile-end-tail plans a fixed tail of `T` frames counted from the end frame for both end kinds. When it lands, set
`minEnd120` to `T - 120` (the frames end 120+ then holds in every run) if `T - 120` is at least 20, and regenerate the
golden; the fixed windows keep their whole span and finish follows as the sum. `minFrames_push` and `minFrames_finish`
keep holding; `minFrames_eq` changes with the value, and `minEnd120_eq_end0` and the `minEnd120` docstring give way to
the tail as the reason.
