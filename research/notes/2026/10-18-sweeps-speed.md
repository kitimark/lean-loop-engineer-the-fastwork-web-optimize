# Breakpoint-gate speed (sweeps-speed)

The workflow `sweeps-speed` ran three read-only researchers, one per question: (A) time, (B) coverage and Lean, (C) CI structure.
The reference is run 39067656223 (flag morph.tween:waapi).

## Answer first
- **The run took 1284 s, but its critical path is only about 451 s.** About 830 s went to waiting for runners. The Free-plan
  cap of 20 jobs is shared by the whole account, one gate run starts 22 jobs, and 4 gate runs overlapped. This is the biggest lever.
- **The sweeps step (312 s Chromium, 267 s WebKit) runs its 4 sweeps one after another.** `--concurrency` only applies to probes.
  The desktop sweep (57 stops) is 72-79% of the step, at about 4.2 s per stop on Chromium and 2.9 s on WebKit. Of that, about
  1 s is fixed sleeps; the rest is animation-settle polling plus collect work, which is not measured yet.
- **Splitting one sweep across jobs is unsound**, because each stop's verdict depends on the whole collapsed history before it
  (Fw.Gate.Scope stopVerdicts). Moving **whole** sweeps between jobs is sound.
- **Proved in scratch (lands with sweeps-lean):** `scopedVerdict_reduce`. Any sweep with the same collapsed key history gives the
  same scoped verdict. So the desktop sweep can drop its 22 stutter stops (57 → 35) without changing any verdict cell, though the
  tally counts change. Also `mergeById_eq_unsharded` with `sharded_verdict_eq`: merging per-id shards equals the unsharded run.
- **Engine install is 45% of all job time.** WebKit spends 31-63 s per job, including a 30 s apt fetch. Caching it saves about
  25-45 s per WebKit job.

## A. Time breakdown

## B. Coverage and Lean obligations

- MEASURED (run 39067656223, job logs): chromium sweeps step 20:48:50→20:54:02. Per sweep: desktop-1512-320-1512 (57 stops) 244.7 s, phone 20.6 s, touch 24.7 s, pain 21.4 s. - INFERRED, by fitting 2L+4r (5-stop sweeps) and 4L+56r (desktop incl. phase-0 loads, run.mjs:105-110): a resize stop takes r≈4.2 s on Chromium and ≈2.9 s on WebKit, against a floor of about 0.65 s (waitResize page.mjs:93-108: 2 frames, 600 ms, then a drain of finite animations capped at 5 s). Per-stop cost is likely the animation drain or collectInPage. Sweeps run one after another (run.mjs:154 for-loop); --concurrency only affects matrix loads.
- CONFIRMED (Scope.lean:73-80, 132-134): under H a sweep's stop i contributes hv(collapse(κ(s0..si))), and rollup depends only on which verdicts occur (rollup_congr Rule.lean:531; tally.verdict = rollup, Rule.lean:147). So for soundness a sweep must reproduce its full collapsed key history: every class change, in order, including the way back up. hv may read the whole history, so both directions are needed. Width adjacency is not needed for scope_sound.
- CONFIRMED: no Lean theorem requires adjacent N\|N+1 stops in a sweep. scope_observes_edges (Scope.lean:557) asks for N\|N+1 only among the scoped LOADS. The current desktop sweep (deskSweepWidths, Scope.lean:481; spec.mjs:82-90) is exactly the minimal list that crosses all 14 width edges ≥320 adjacently in both directions (kernel-checked in scratch). 'edge-1' adds nothing: whole-px widths flip width<=N only between N and N+1 (sweeps_reachable; fractional gaps are unreachable).
- MEASURED in Lean (#eval / decide +kernel, scratch SweepInst.lean): the desktop sweep's collapsed history under truth key (30 conds) together with all 14 part keys has 35 classes, so 22 of its 57 stops are stutters. With part keys alone it is 25. Part-read desk width edges are only {400,600,640,720,860,960,1000,1100}. No part reads 461, 480, 1030, 1279 or 1511; those are needed only by the truth rows (summary.mjs:11, evaluated at every stop, summary.mjs:74-77).
- PROVED in scratch (compiles, no sorry; SweepReduce.lean): mem_stopHist_iff (the stops see exactly the nonempty prefixes of collapse), stopVerdicts_mem_of_collapse_eq, and scopedVerdict_reduce: replacing each sweep by one with the same collapsed key history keeps scopedVerdict. Kernel-checked instances: R3 (45 stops) keeps the truth key and all 14 part-key histories and keeps adjacency for the 8 part-read edges. R2 (35 stops, stutter-free) keeps all histories. A morph.tween-only run needs 9 stops.
- CAVEAT: a reduced sweep keeps the verdict cell but changes the tally counts (FAIL k/n denominators, State.lean blockCell), and it weakens detection of H failures that only show live at unread edges. Settle timing is outside Lean: the only guard is the hysteresis pair (State.stale, State.lean:605), which checks only the final stop of each sweep. The original's main resize listener looks rAF-throttled (snapshot 2.DyWL8TcE.js, rE/tE) rather than timer-debounced (INFERRED).

## C. CI structure

- MEASURED (run 39067656223): the run took 1284 s but its critical path without queueing is only ~451 s (plan 5 + site 35 + sweeps 345 + merge 36 + gaps). ~830 s was spent waiting for runners: plan waited 149 s, site 131 s after plan, and the webkit sweeps job started 576 s after site ended. That job was the last to finish (896->1241 s, merge 1248-1284 s).
- MEASURED: in this run at most 5 jobs ran at once, ~2.3 on average over the fan-out (2155 job-seconds of gate + sweeps work spread over 921 s). Cause: the Free-plan 20-job cap is shared by the whole account (research/notes/2026/10-17-ci-trigger-scope.md:22). `gh run list` shows four breakpoint-gate runs (20:33-21:01), plus gate-gaps, chromium-counts, lean, mutants, wktr and webkit-sim, all overlapping. The repo is PUBLIC (gh repo view), so runners are free but the cap still applies.
- CONFIRMED (breakpoint-gate.yml:70-292; run.json lists 22 jobs): one run starts 22 jobs (plan, site, 16 gate, 2 sweeps, 2 merge). Right after site, 18 jobs are ready at once, so a single run nearly fills the 20-job cap by itself. MEASURED: the sweeps job did queue behind shards. 9 gate shards started before 'sweeps (playwright-webkit)'.
- MEASURED (task-a logs of the same run): the sweeps run one after another (run.mjs:154 for-loop; --concurrency only applies to probes). Chromium: desktop-1512-320-1512 245 s, phone 21, touch 25, pain 21. WebKit: desktop 191 s, 26, 27, 23. The desktop sweep has 57 of the 72 stops (spec.mjs:83-92), about 4 s per stop. That makes it 72-78% of the sweeps step and the floor for any single job.
- MEASURED: setup is 45% of all job time. 2265 job-seconds in total, of which 1239 s is probe/sweep work and 583 s is engine install (gate-engine). WebKit install takes 31-63 s per job. In the sweeps job, 30 s of it is the apt fetch of system deps ('Fetched 106 MB in 30s'). The WebKit browser download itself takes 2.5 s. Chromium probe shards spend 22-24 s on probes versus ~33 s of setup. WebKit shards spend 54-67 s versus ~70 s.
- CONFIRMED: splitting one sweep across jobs (for example the 1512->320 leg and the 320->1512 leg) is unsound. The verdict at each stop depends on the whole history before it: stopVerdicts uses collapse(stops.take (i+1)) (lean/Fw/Gate/Scope.lean:79-81), and a fresh load at 320 has a different history. Only whole sweeps can be moved between jobs.
- CONFIRMED: merge-gate.mjs has no Lean model. grep finds only Fw/Store/Ci.lean (chromium-counts shards) and Fw/Sched/ParMetrics.merge (intervals).
