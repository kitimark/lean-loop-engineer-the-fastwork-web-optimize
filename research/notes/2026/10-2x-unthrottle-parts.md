# Which parts the throttle reaches, and what unthrottle changes, per part

Task `unthrottle-parts-lean`. Lean: `lean/Fw/Device/ThrottleParts.lean` (module `Fw.Device.ThrottleParts`). Golden:
`packages/contracts/golden/device/throttle-parts.jsonl` (33 lines, generated by `lean/scripts/ThrottlePartsGolden.lean`).
WebKit cites `@862f17d`. Part paths are under `apps/site/src/parts/`. Inputs: `10-2x-scroll-throttle-parts.md`,
`10-2x-toolbar-throttle.md`.

## Answer first

- **9 parts are hit, 9 are harmless, 5 are not hit.** Each part's class comes from the Lean decision `reach` applied to
  its source and shape, and each source and shape is a premise cited at file:line in the table below. CONFIRMED in Lean
  (`hit_parts`, `namedNotHit_reach`). The premises are read from the code, not proved.
- **A part that shows a strictly monotone function of scrollY freezes for throttleK frames once per update under the
  throttle (5 frames at 60 Hz), and never when the throttle is lifted.** Proved: `hit_throttled`, `curve_lifted`. Today
  that covers hero.exit (faithful) and platform.shrink.
- **engine.scroll:unthrottle lifts it for every main-thread reader at once.** On any engine where scroll timelines are
  supported, the flag gives the lifted mode, so a part whose shown value never repeats has no still run. Proved:
  `mode_withLift`, `unthrottle_no_stills`, from `Fw.Parts.EngineScrollUnthrottle.lift_effect`.
- **Threaded and time-based parts show the same frames with and without the throttle.** Proved: `threaded_same`,
  `time_same`. The phone's fade series (0 band runs in every pass, `10-2x-scroll-throttle-parts.md`) fits this.
- **Predicted phone outcome per recorder key:** `hero` shows still runs of 5 frames throttled and none lifted; `people`
  shows pulses (no fixed-length still runs) throttled and none lifted; `fade` shows no still run in either mode (golden
  lines 25-27).
- **Follow-up candidates:** platform.shrink and hero.exit can move to a threaded timeline with the same look (hero.exit
  already has `:threaded`). morph.mount and morph.tween have the root-lock candidate, which changes the look. Every other
  hit part has no same-look fix besides unthrottle (list below).

## The model

The compositor scroll offset at frame `t` is `u t`. The web process sees `seen m p u t`:

- throttled: `u (p * (t / p))`, the offset at the last update frame, with one update per `p = throttleK d + 1` frames.
  At 60 Hz (`d = 1667` hundredths of a ms) `p = 6`, as in WKWebViewIOS.mm:3256-3268, which delays an update until 100 ms
  after the last one while Safari changes the toolbar insets interactively.
- lifted: `u t`, one update per frame (WKWebViewIOS.mm:2384-2399).

A part shows `f (seen m p u t)` (main-thread reader), `f (u t)` (threaded scroll-driven animation) or `f t` (time). Still
runs are counted with `Fw.Device.StillRuns.runs` on the part's own value series, with rows `(v, v)`: a run is a stretch of
equal values ended by a change, and the band keeps runs of 5 to 6 frames with the value strictly between 0 and 1000 (per
mille). Which mode applies is `modeOf`, from `Fw.Parts.EngineScrollUnthrottle.throttledOn`.

## The theorems in plain words

| Theorem | Says |
|---|---|
| `throttled_delay` | Throttled, a main-thread reader shows at frame `t` the value it would show lifted at frame `p * (t / p)`, at most `p - 1` frames earlier. It holds for every `f`. |
| `distinct_of_strict` | A pass that moves one way, with `f` strictly increasing or decreasing on the offsets it visits, gives a shown value that differs at every two frames. |
| `curve_throttled` | Throttled, over `p * n` frames such a reader has exactly `n - 1` still runs, each `p - 1` frames long. |
| `curve_throttled_band` | If every shown value is strictly between 0 and 1000 and `p - 1` is 5 or 6, all `n - 1` runs are band runs. |
| `hit_throttled` | For frame intervals from 14.29 to 19.99 ms (50 to 70 Hz) the run length is `throttleK d`, and the band count is `n - 1`. |
| `curve_lifted` | Lifted, such a reader has no still run at all. |
| `constant_harmless` | A reader whose `f` is constant on the pass shows the same value in every frame in both modes, and has no still run. |
| `threaded_same`, `time_same` | Threaded and time-based parts show the same frames in both modes. |
| `threaded_no_stills`, `time_no_stills` | Such a part whose value changes every frame has no still run in either mode. |
| `mode_baseline` | iOS WebKit, insets changing, no main-thread scroll-driven animation reported: throttled. |
| `mode_withLift`, `unthrottle_no_stills` | With the flag on a page that supports scroll timelines, every engine is lifted, and a never-repeating main-thread reader has no still run. |
| `mode_idle`, `mode_chromium` | Toolbar still, or Chromium: lifted. |
| `throttleK_120hz` | At 120 Hz (8.33 ms) the run is 12 frames, outside the 5-to-6 band. ProMotion is a stated constant here, not measured. |

The shape of a part decides its class (`reach`, one theorem per branch, `reach_curve` to `reach_time`):

| Shape | Meaning | Class | Rests on |
|---|---|---|---|
| curve | shown value strictly monotone in scrollY on its range | hit | `hit_throttled`, `curve_lifted` |
| chase | eased each frame toward a curve target | hit | the target is a curve |
| capture | reads scrollY once, later scrolls back to it | hit | `throttled_delay`: the value is up to `p - 1` frames old |
| step-look | a class or colour flips at a scroll threshold | hit | `throttled_delay`: the flip is up to `p - 1` frames late |
| step-idle | a threshold starts or pauses a time-based animation | harmless | `throttled_delay`, then `time_same` |
| constant | constant on the moving range | harmless | `constant_harmless` |
| no-read | reads no scroll on moving frames | not hit | none |
| any shape, threaded or time | | not hit | `threaded_same`, `time_same` |

Where this differs from `10-2x-scroll-throttle-parts.md`:

- **pain.notes** is step-look, not a curve. Its scroll callback only tests `covered()` (card top below 0.995 of the
  viewport, `pain.notes/driver.ts:134-137`) and re-commits the view (`:214-218`). The notes do not move with scroll, so
  the symptom is a clear that comes up to 5 frames late, not notes moving in steps.
- **people.card and commission** are chases (`lerp` with RATE 0.22, `people.card/logic.ts:48-51`; GAIN 0.22,
  `commission/logic.ts:46-63`). The shown value keeps easing between updates, so it pulses rather than holding still.
  This fits the phone's low people-zone rate with lift ("few frames").
- **engine.scene, platform.entries, platform.visuals** start or pause time-based work at a threshold, so they are
  harmless here; the earlier note marked them hit with "late reveal".
- **morph.countdown** pauses through an IntersectionObserver (`morph.countdown/index.tsx:40`), like morph.columns, so it

- **platform.shrink** is a curve only on its ramp: `raw` is 0 for card bottom at or above 0.85 of the viewport height
  and 1 at or below 0.35 (`platform/logic.ts:17-21`). Where it stays 0 or 1, as INFERRED at the page end,

## Follow-up candidates

- **platform.shrink, then hero.exit:** curve parts. A threaded scroll timeline gives the same look because the value is
  a pure function of scroll (`followUp` = threaded-timeline). hero.exit already has `:threaded`; platform.shrink has no
  threaded variant yet.
- **morph.mount, morph.tween:** captures. A root lock in place of `scrollTo(pin)` ends the restore fight, but it changes
  the look (rank 2 in `10-2x-scroll-throttle-parts.md`), so it needs the user's visual review.
- **people.card, commission:** chases. A threaded version drops the easing, which changes the look, so unthrottle is
  the only same-look fix. Proving the pulse (a bound on the eased step after each update) is open.
- **nav, nav.hitTest, pain.notes:** step-look. Only unthrottle fixes them.

## Limits

- WebKit behaviour enters as premises cited from source; it is not proved.
- No CI run in this task; task `unthrottle-parts-measure` measures the predictions.
- 60 Hz cadence as in `Fw.Device.StillRuns`. At 120 Hz the run is 12 frames (`throttleK_120hz`), outside the band.
- The theorems take `p * n` frames, so a pass ends on an update boundary, and they take one-way passes. A trailing
  partial update adds nothing, because `runs` drops a trailing run.
- The phone recorder's `hero` key is not written under `hero.exit:threaded` (`hero.exit/threaded.ts:144` removes the
  inline property), so that variant has no hero series to compare.
