# Chromium window reader: why morph.stage reads noData in every end window, and the own-end rule

Tags: MEASURED (CI run id named), CONFIRMED (Lean theorem or source cited), INFERRED (reasoned, not seen).

## Answer

* The windows were already cut from each run's own end frame (`offscreen-windows.mjs:44-49`, Lean `Run.windows`). The
  refusal is the equal-length rule: `usableOn` (`packages/measure-chromium/src/offscreen-windows.mjs:79-80`, Lean
  `usableOn`) asks `sameWindow` (`offscreen.mjs:61-63`, Lean `Offscreen.sameWindow`) that every run of both arms has one
  positive frame count in the window. CONFIRMED by the numbers below. The run count (3 per arm), the key check and the
  slack are not what refuses.
* The lengths differ because the flag run has almost no frames after its end. MEASURED on counts.json of the six runs
  below: the base run ends at frame 574 and records 771 frames (last frame 741, 167 after the end); the morph.stage run
  ends at frame 670 and records 703 frames (last frame 673, 3 after the end). Window cuts are clipped to the last frame
  (`pushWindows`, `offscreen-windows.mjs:23-31`), so the stage windows hold 3 / 0 / 0 / 0 / 37 frames where the base
  holds 20 / 40 / 60 / 47 / 201.
* Why only 3 frames follow the end (INFERRED from `packages/measure-chromium/src/run.mjs:417-422` and the phases in
  counts.json): the swipe planner is told `ended` on the frame the page end is reached and stops when its current
  stroke is done; the base run swiped on for 164 frames (swipe phase 11-738), the stage run for 0 (swipe phase 11-670).
  The page is 860 px longer with the stage (`scrollY` maximum 6202 against 5342, MEASURED), which moves the end frame
  and the stroke phase it falls in.
* So the premise "the windows are taken from a common frame" was refuted: they are not. The data the old rule needed is
  missing in the stage run, not misaligned. No window reader can compare frames 20-59 after the end when one arm has
  none.

## The rule (PROVED, `lean/Fw/Measure/OffscreenWindows.lean`)

A window keeps its start at the run's own end frame (or its approach start). Its length for the comparison is the
shortest it has in any run of either arm (`commonLen`), and every run's window is cut to that many frames
(`Win.cap`, `Run.capped`); the verdict is the existing one on those cut windows (`ownVerdicts`).

| statement | theorem |
|---|---|
| a cut window has `min len m` frames | `Win.cap_len` |
| a window of at most `m` frames is unchanged | `Win.cap_of_len_le` |
| a cut window has at most the common number of frames | `vecsOf_capped_n_le` |
| a window that is the same length in every run gets today's verdict | `ownVerdicts_eq_window` (via `cap_ge_of_same_len`, `ownVecs_eq`) |
| every run ends on the same frame and has the same last frame: all windows are today's | `ownVerdicts_eq_of_same_end` |
| a gain needs `minRuns` valid runs per arm | `ownVerdicts_gain_needs_runs` |
| fewer than `minRuns` valid base runs: every window noData | `ownVerdicts_noData_of_fewBase` |
| fewer than `minRuns` valid flag runs: every window noData | `ownVerdicts_noData_of_fewFlag` |
| no frame in common (common length 0): the window is noData | `ownVerdicts_noData_of_noFrames` |

The equal-length case needs both the same end and the same last frame: with the same end and different recording
lengths today's reader refuses the long windows (end 120+, finish), and the own-end rule compares their common frames
(golden case "same end frame, the flag recorded 46 frames longer"). A run with no frame or a short counter column has
no plan and is not counted as a run.

Golden: `packages/contracts/golden/measure/offscreen-windows.jsonl`, new `op: "own"`, 10 cases generated by
`Fw.Measure.OffscreenWindowsGolden`. The TS reader (`ownVerdicts` in `offscreen-windows.mjs`) is a copy of the Lean
functions checked against it by `test/offscreen-windows.test.mjs`; it holds no other decision logic. `summarizeArm`
(the CLI table) now uses the own-end rule and prints the compared frame count per window.

Runs: base 40339630528, morph.stage flag 40339622735 (both `chromium-counts`, profile `swipe-touch-v1`, artifacts
`chromium-counts-rewrite-r1..r3`, 3 runs per arm). Table and per-run windows: `results/window-own-end/morph-stage.md`
and `morph-stage.json`.

| finish | 37 | noData | noGain | less RecalcStyleCount 141 to 100, Paint 293 to 281, FireAnimationFrame 131 to 86; more LayoutCount 10 to 31, RasterTask 351 to 656, PaintImage 199 to 641 |

Reading (the morph.stage verdict itself belongs to the morph-stage task):

* The windows that can be read are approach (34 frames) and finish (37 frames), both `noGain` with the stage adding
  layouts, rasters and decoded images.
* End 0-19 reads `gain` on 3 frames. That is weak: the base 3 frames after its end are still inside a swiping run (164
  more swipe frames follow), the stage 3 frames are the last of its run. Treat it as an artifact of different stroke
  phases (INFERRED), not as a gain at the end of the page.
* End 20-59, 60-119 and 120+ stay noData: the stage run has no frames there. A measurement of the page end with the
  stage needs a recording with at least 120 frames after the end.

## Follow-ups (outside the unit)

* Profile or run rule that guarantees a fixed number of frames after the end (for example a tail counted from the end
  frame, not from the stroke that happened to finish), so end windows exist in every arm. Needs new CI runs.
* A minimum frame count per window (the rule here compares 3 frames when 3 exist); none is specified.
