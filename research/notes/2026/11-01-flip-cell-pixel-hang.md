# flip-cell-pixel-hang: why WebKit flip-cell stalled in "Pixel look report" and read 0 columns, and the bounded fix

Date: 2026-11-01. Task `flip-cell-pixel-hang` (graph r613). CI branch `ci/flip-cell-pixel-hang`.
Lean: `lean/Fw/Parts/MorphGeomReady.lean` (`cellReady`, `waitStep`, `cellOutcome`, `retryNext`, `cellsPass`, `cellsKept`, limits), `lean/Fw/Parts/MorphGeomVerify.lean` (`leaveCountOk`, `bandOk`, `runVerdict`); golden lines `verifyReady`, `verifyWait`, `verifyAttempts`, `verifyNext`, `verifyErr`, `verifyCells`, `verifyLimits`, `verifyLeaveCount`, `verifyRun` in `packages/contracts/golden/morph-geom-timed.jsonl`.
Code: `packages/gate-breakpoints/src/bounded.mjs`, `flip-cell.mjs`, `flip-verify.mjs`, `packages/premise-tests/src/look.mjs`; steps in job `flip-cell` of `.github/workflows/breakpoint-gate.yml`.

## Answer

- (A) Pixel look report stall. INFERRED: the 640x1000 band at device pixel ratio 3 makes a 1920x3000 WebKit screenshot on a software-rendered ubuntu-24.04-arm runner; on a slow host that call outlives Playwright's 30 s default, and the harness had no bound on the page calls and closes around it, so a hung call held the step until the job was cancelled.
  - Evidence (MEASURED from the failed-run logs): 41214042166 and 41214032493 died with `page.screenshot: Timeout 30000ms exceeded` at `packages/premise-tests/src/look.mjs:236` (the flag-page screenshot) in the 640x1000 band (6 min into the step in 41214032493, after the 640x1000 m=0, 0.25 and 0.5 cells had read in 19 s and 15 s); 41214035220 and 41214038309 produced no output for 2422 s until cancelled. Passing 41211006218 took 8.5 min for the same step.
  - Telemetry of the stalled run 41214042166: memory used peaked at 6764 MB against 4779 MB in 41211006218, CPU peaks equal (98 and 99 percent). The date is pinned in `PIN_SRC`, so wall-clock is ruled out. Same sha 08fc651a3 and same runner image: the difference is the host (INFERRED; no artifact shows the host fault itself).
  - Why it hung and not failed: `close()` of pages and browser, and every `page.evaluate`, had no timeout, and the screenshot used the 30 s default.
- (B) `columns: 0, expected 3; images: 0, base 13` at 640x1000 m=0 (runs 41214032493 and 41186783098). INFERRED: the morph panel mounts through an IntersectionObserver (rootMargin 200 percent), and with requestAnimationFrame at 2 to 6 Hz the flag page was read before it mounted; the fixed 1200 ms sleep was the only wait. In the logs the same band reads `ok` on the next m values, so the page was right once it had mounted. Run 41189419989 is a different failure of the same family (`lang: edges differ by 80.97 px`, earn width 32 against 108.97: a nav width transition still running at the read); it is covered by the same signal (no running transition).
- Fix, with every rule in Lean first:
  - Ready signal (`cellReady`): flag shows the band's column count, same image count as the base, every image of both pages loaded, no CSS transition running on either page. Per-branch theorems: `ready_no_columns_waits`, `ready_missing_images_waits`, `ready_unloaded_waits`, `ready_base_unloaded_waits`, `ready_flag_moving_waits`, `ready_base_moving_waits`, `ready_mounted_reads`.
  - Bounded wait (`waitStep`): poll every 250 ms up to 20 s, then `late`. `late` still takes the reading and judges it (`late_same_as_read`, `late_defect_fails`), so a real defect (wrong columns) still fails after the wait.
  - Named limits (golden `verifyLimits`, `limits_ordered`): ready 20 s, poll 250 ms, screenshot 120 s, page call 60 s, close 15 s, 2 attempts. Every Playwright call goes through `bound(name, ms)` and fails with `<name>: no answer in <ms> ms`.
  - Retry only for faults: a stalled call is a fault, never a reading. A cell is retried on fresh pages up to 2 attempts, and the first reading decides (`errKind`, `err_limit_is_stall`, `err_timeout_is_stall`, `err_other_is_defect`, `err_stall_is_fault`; `firstReading`, `retry_defect_stays_fail`: a failing reading is never retried into a pass; `outcome_pass_has_reading`: a pass needs a reading; `retry_reading_done`, `retry_fault_again`, `retry_fault_stops`). All faults give `exhausted`, which fails flip-cell (`cells_pass_exhausted_fails`) and fails look (`cells_kept_exhausted_fails`); look keeps failed readings as reported rows (`cells_kept_reports_fail`).
  - Fault notes (load average, free memory, screenshot ms, time) go into the JSON (`faults`, `shotMs`) so the next stall is explained from an artifact.
  - Step timeouts in the workflow: 15 min (Flip-state cell), 15 min (geom-timed), 40 min (Pixel look report; passing run 8.5 min).
- (C) flip-verify review follow-up: the probe resets `sawOn` and `leaveTs` at each cycle start (`beginCycle`); A4 requires leave count = cycle count (`leaveCountOk`: `leave_count_short_fails`, `leave_count_extra_fails`, `leave_count_none_fails`, `leave_count_exact_passes`, `leave_count_no_cycles_fails`); the run verdict (`runVerdict` = bands non-empty, every band ok, retry judged) is Lean with theorems `run_empty_fails`, `run_unjudged_retry_fails`, `run_band_fails`, `run_passes`, `band_a3a_fails`, `band_a4_fails`, `band_a5_fails` and golden lines `verifyLeaveCount`, `verifyRun`, replayed in `packages/gate-breakpoints/test/flip-verify.test.mjs`.

## Accepted limits

- The root cause of the slow 640x1000 WebKit screenshot is not proven (INFERRED host slowness). On a bad host both attempts can fault; the step then fails fast with a named message instead of hanging. Which limit fires first: the flip-cell job limit is 90 min and the named step limits are 15 + 15 + 40 = 70 min, plus the Flip verify, repeats and mutation steps (9.2 min in run 41231318047; the steps before Pixel look took 18.7 min in run 41234736854), so about 80 min in the worst case with those steps as measured: a named step limit fires first with about 10 min to spare. The Flip verify, repeats and mutation steps have no page-call bounds yet; if one hangs, the job limit fires and gives the old `cancelled` result (follow-up: bound the Flip verify page calls).
- Only stalls are faults (`errKind`: `LimitError`, `TimeoutError`). Any other thrown error (a page-side TypeError, a closed browser) is a defect: `takeCell` rethrows it after attempt 1, the step fails, and nothing is retried into a pass (`err_defect_not_retried`, `err_defect_first_fails`). A crashed browser therefore fails the step on the first attempt instead of being retried.
- A mutation that changes the column count makes a cell wait up to 20 s before the (failing) reading; the mutation still fails.
- `look.mjs` per-cell loop is glue with no local test (TS stand-in); the decision rules it calls are golden-checked in `bounded.test.mjs`.
- Chromium flip-cell is out of scope (it shares no failure here); no site change; no tolerance changed.
