The core idea

A two-speed loop

The inner loop runs on every change and never touches the phone: it counts the engine's work in Chromium and WebKit on GitHub Actions (not on the Mac, where agents and sleep disturb runs) and screens the result with a proved rule. The outer loop is the phone, an optional spot check in sessions the user starts on demand; it has no dependents (D1) and is never the evidence for a landing.

No one moves a card from stage to stage. Each stage is derived from evidence events keyed by the build commit, so a new build sends the card back to screen and voids older screen, review and device evidence.

Measurement

Count the work, then price it

Timing changes with heat, load and the device. The amount of work an engine does in a frame does not: how many styles it recalculated, how many layouts it ran, how many pixels it repainted, how many layers it built. v2 steps the page one virtual frame at a time, reads those counts and compares the original with the variant. No cost model is fitted (Q37 resolved, rev 10).

Chromium · development aid

Headless Chrome in a Linux container on GitHub's arm64 runners, because frame stepping (BeginFrameControl) is refused on macOS. The page's own clock advances; animations are never seeked, so compositor animations stay on the compositor. There is no Android phone, so no Chromium coefficients are fitted.

The WebKit cost model of revisions 7 to 9 (not fitted in v2)

dt ≈ max( T_req , W + F + U + δ ) W = J + Σ c·counts F = max( s²·Ap / R_cg , Bn / R_alloc ) T_req = 16.67 ms

W is main-thread work, F the GPU raster wait, U the UI-process apply. Revision 10 fits no coefficient and claims no cost model (Q37 resolved); the evidence is the theorem pair per part and optimization (PLAN §4.7). The shape stays: every coefficient is non-negative, so removing work can never raise a prediction.

Sheet mutations are a count family of their own. In a spike, inserting 100 CSS rules during the scroll left every other planned count unchanged; only style-recalc time rose (20–24 vs 8–10 ms). The original reads 0 after load, and fixture K10 would price one insertion (not run in v2, PLAN §4.4).

The screening rule needs no calibration

If a variant's count vector is no higher than the baseline's in every component of every frame, and lower somewhere, its predicted cost cannot be higher under any non-negative coefficients. That is a theorem in Lean. A change that passes it is "less work" and can land without the phone, provided the counted vector covers everything the change touches.

Measurement · what the runs showed (revision 7.1)

Byte identity was too strict, so counts are classed per type

Whole count files are never byte-identical (thread ids, GC, async work). Each count type is classed deterministic, stable or quarantined. Chromium: stable means at most 4 frames differ and run totals differ by at most 24 count units, over 3 runs; pixel-area types allow up to 1/1000 of their smallest total. WebKit: a tolerance per cell, 2 passes in each of 2 boots.

How classes are used (decided). Deterministic types are compared frame by frame. Stable types are compared only as run totals, with a proved margin of 2t. Quarantined types are never used. A type's signed class is its worst over at least 3 CI runs, because classes drifted between runs of the same code. In the frozen table trace.Paint is quarantined, so Chromium paint is not screened; paint terms come from WebKit counts, or from raster counts where those are stable.

The full findings table, with CI run ids, is in research/notes/2026/10-17-plan-evidence.md §3.3 (moved out of the plan in revision 8).

MUI everywhere, static styles at scroll time

Runtime CSS-in-JS would insert styles while the page scrolls and add to the very costs being measured. So MUI's Emotion styles are rendered at build time ("Emotion AOT"): a build-only census route renders every MUI component in every state the parts declare, and the styles go into one static mui.css in @layer mui. Before hydration the client marks every style as already inserted, so Emotion inserts nothing after first paint; in measurement builds one miss fails the build.

Pigment CSS, the compiler the user remembered, is a paused alpha that no longer builds with current MUI. It stays the whole-site fallback and an optional measured arm. Rules S1–S13 (no sx, styled or css in parts; no per-frame value through React; care with Tabs, Avatar, transitions and ripples) are enforced by lint. Spike SPK-r checks the pipeline before any part is built with MUI.

Every breakpoint of the original, identically, for every part

  • Generated list. breakpoints.json is extracted from the original's CSS (media queries) and JS (width, touch, hover and pointer gates), per part. The inventory found 30 distinct media conditions and 18 edges. The Lean breakpoint model generates breakpoints.gen.json, and the build fails unless it equals the extracted file.
  • Pure 860 is not the 860 combo. A touch tablet at 861–1200 px or a phone in landscape takes the desktop path for some parts and the compact path for others. The rewrite keeps the two conditions apart, and the gate tests both paths (1024 touch, 932×430).
  • Breakpoint lint in fw gate: fails when a part uses a breakpoint the original does not, or misses one the original uses for that part.
  • Breakpoint gate before any part is promoted: PL0–PL3, original vs rewrite, at both sides of every edge, in every touch, hover and pointer combination the original distinguishes: 124 loads per engine (an estimate) in Chromium and Playwright WebKit, plus live-resize sweeps across every edge.
  • faithful-with-delta never covers a missing or shifted breakpoint. Each PR runs a fast core set of viewports; one Simulator check closes promotion.
  • Cells the harness cannot reach (decided, Q33). Chromium reaches the fractional gaps (zoom 200 %, odd widths) and the hover × pointer cross; WebKit cannot, because its media width is a whole number and hover and pointer come from one constant. Such a cell gets the state unreachable in the Lean gate, and a Simulator or device check settles it.
  • Status. The 4 pilot parts pass the 14 PL0–PL2 cells in both engines; the gate's verdict now runs in Lean (0d02aff).
Lean 4.35.0 · elan 4.2.4 from Homebrew

Lean first for everything reproducible

Every pure piece of the console, the site, measurement and tooling is specified and proved in Lean before it is coded. Then Lean reaches the code in one of three ways: it runs in fwcore, Lean generates it (constants, CSS media strings, JSON such as breakpoints.gen.json, test matrices), or the TypeScript/React code must pass Lean golden vectors. Only I/O, rendering and glue stay unproved.

The kickoff inventory found 87 decisions, state machines and pure functions, each at a proof level. One long-lived Lean program, fwcore serve, holds the console state and makes the decisions; TypeScript only moves data. A Node → fwcore round trip measured 17.6 µs, and 100k events replay in under a second.

Evidence, not a go/no-go

Each L1 module ships with mutants: v1 bugs put back on purpose, each of which must break the build. A bug ledger records, per module, what caught each bug. A module whose proofs cost more than one agent-day on two consecutive changes while catching nothing moves to L2 by a decision record. Lean as a whole is not on trial at M4. The M0 pass: 625 mutants, 621 caught, 4 that do not compile or do not change behaviour, 0 survived (8074907).

Cost and packaging

The estimate was about 20 modules and roughly $700–1,100 of Lean work; at commit 7d564e2 the Lean core had 1,947 declarations (910 theorems) in 51 modules (measured; the same figure as the plan). The core needs no Mathlib; a proof that does goes in a separate FwMath package that Fw never imports. The browser's flag resolver is checked against Lean on every single-part override of every preset, plus 2,000 generated multi-part cases.

Coordination rules from the chat history

  • No recurring AI check prompts: scripts watch instead. fw watch computes team health in Lean (5 agent states, 14 alert codes) and wakes the lead only on an alert; the device watcher and a notice coalescer do the rest.
  • Nobody writes status: fw land --task <id> writes a Task: trailer, and the trailer marks the work-graph task done.
  • The lead watches for work that runs long against its estimate, and moves load-heavy work to CI (the mutation pass drove the Mac's load to about 500).
  • Kill only processes your own run started; pkill and killall are denied after an agent closed the user's browser.
  • Workers send results to their consumer; the lead gets ≤ 300 characters and a file path.
  • Agents cannot write console state: a strict sandbox and deny rules guard the gitignored .fw-console/, and console-api is its only writer.
  • Agent caches last 5 minutes (measured), so an agent idle longer with over 30k tokens of context is stopped and a fresh one starts from its handoff note.
  • After every compaction a hook will re-inject the roster, names and the lead's address (planned).
  • One plain command per Bash call; multi-step work is a committed pnpm fw command.
  • main moves only through the lead's fw land (ff-only); any other move shows up as a violation on the user's needs-you list.

Math on the page you read · on demand

The user reads math, not Lean

Lean source holds the specs, the proofs and the code; each declaration has a one-line English docstring that says what it is for. When the user should read some theorems, their math is written onto the page that shows them: the lead names the declarations, a lean-prover exports each one with lake exe mathview --decl <name> (its signature, axioms and statement hash) and writes its math from the Lean, and a fresh math-reviewer writes its own math from the Lean first, then compares the two clause by clause. The lead fixes the page from a disagreement and asks a new reviewer until every row agrees. The procedure is docs/team/tools/math-artifact.md.

An agree row is recorded with the declaration's statement hash. It holds while the Lean statement is unchanged, so editing a theorem makes its row stale and editing a docstring does not. The build refuses sorry and non-standard axioms (the axiom check).

New to Lean? Math to Lean is a study page that walks through twelve declarations of the kickoff sketch, from a one-line def to the lease invariant, and lines up each math fragment with the Lean that states it.

What the reviewer compares

Quantifier scope and binders; number domains (ℕ vs ℤ vs ℚ); truncated subtraction and rounding down; ≤ vs <; the empty input; list count vs set membership; ⇒ vs ⇔ and which direction is proved; a hypothesis the proof does not need. Until 2026-10-19 the docstrings carried this math for every declaration and a generated math view showed it; math-final ended at 5,109 agree, 0 disagree, 517 stale, 1,373 pending. That view is retired.

What the theorems do not say

Writing exact math is what found these. The lease's FIFO theorem covers one release step; a holder can still renew forever, so "no starvation" is false today (default Q26 adds a cap). step_inv is one step, not every reachable state. Unit costs are whole µs, so 0.3 µs per element cannot be written yet.
