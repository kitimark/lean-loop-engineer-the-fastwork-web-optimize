The core idea

A two-speed loop

The inner loop runs on every change and never touches the phone: it counts the engine's work in Chromium and WebKit and screens the result with a proved rule. The outer loop runs in phone sessions the user books. It calibrates the cost model and licenses kinds of change to land without the device.

No one moves a card from stage to stage. Each stage is derived from evidence events keyed by the build commit, so a new build sends the card back to screen and voids older screen, review and device evidence.

Measurement

Count the work, then price it

Timing changes with heat, load and the device. The amount of work an engine does in a frame does not: how many styles it recalculated, how many layouts it ran, how many pixels it repainted, how many layers it built. v2 steps the page one virtual frame at a time, reads those counts and feeds them to a cost model.

Chromium · development aid

Headless Chrome in a Linux container, because frame stepping (BeginFrameControl) is refused on macOS. The page's own clock advances; animations are never seeked, so compositor animations stay on the compositor. There is no Android phone, so no Chromium coefficients are fitted.

The WebKit cost model, per frame

dt ≈ max( T_req , W + F + U + δ ) W = J + Σ c·counts F = max( s²·Ap / R_cg , Bn / R_alloc ) T_req = 16.67 ms

W is main-thread work, F the GPU raster wait, U the UI-process apply. Every coefficient is fitted on the phone and constrained to be non-negative, so removing work can never raise a prediction.

Sheet mutations are a count family of their own. In a spike, inserting 100 CSS rules during the scroll left every other planned count unchanged; only style-recalc time rose (20–24 vs 8–10 ms). The original reads 0 after load, and fixture K10 prices one insertion on the phone.

The screening rule needs no calibration

If a variant's count vector is no higher than the baseline's in every component of every frame, and lower somewhere, its predicted cost cannot be higher under any non-negative coefficients. That is a theorem in Lean. A change that passes it is "less work" and can land without the phone, provided the counted vector covers everything the change touches.

MUI everywhere, static styles at scroll time

Runtime CSS-in-JS would insert styles while the page scrolls and add to the very costs being measured. So MUI's Emotion styles are rendered at build time ("Emotion AOT"): a build-only census route renders every MUI component in every state the parts declare, and the styles go into one static mui.css in @layer mui. Before hydration the client marks every style as already inserted, so Emotion inserts nothing after first paint; in measurement builds one miss fails the build.

Pigment CSS, the compiler the user remembered, is a paused alpha that no longer builds with current MUI. It stays the whole-site fallback and an optional measured arm. Rules S1–S13 (no sx, styled or css in parts; no per-frame value through React; care with Tabs, Avatar, transitions and ripples) are enforced by lint. Spike SPK-r checks the pipeline before any part is built with MUI.

Lean 4.35.0 · elan 4.2.4 from Homebrew

Lean first for everything reproducible

Every pure piece of the console, the site, measurement and tooling is specified and proved in Lean before it is coded. Then Lean reaches the code in one of three ways: it runs in fwcore, Lean generates it (constants, CSS media strings, JSON such as breakpoints.gen.json, test matrices), or the TypeScript/React code must pass Lean golden vectors. Only I/O, rendering and glue stay unproved.

The kickoff inventory found 87 decisions, state machines and pure functions, each at a proof level. One long-lived Lean program, fwcore serve, holds the console state and makes the decisions; TypeScript only moves data. A Node → fwcore round trip measured 17.6 µs, and 100k events replay in under a second.

Evidence, not a go/no-go

Each L1 module ships with mutants: v1 bugs put back on purpose, each of which must break the build. A bug ledger records, per module, what caught each bug. A module whose proofs cost more than one agent-day on two consecutive changes while catching nothing moves to L2 by a decision record. Lean as a whole is not on trial at M4.

Cost and packaging

About 20 modules instead of 4, and roughly $700–1,100 of Lean work instead of $280 (an estimate). The core needs no Mathlib; a proof that does goes in a separate FwMath package that Fw never imports. The browser's flag resolver is checked against Lean on every single-part override of every preset, plus 2,000 generated multi-part cases.

Math view: the user reads math, not Lean

Every theorem, and every definition the user is expected to read, carries one English sentence and its math in its docstring. In the project, lake exe mathview builds this view on every build. The build fails when math is missing, a sorry remains, or the Lean (or any definition it uses) changed after the math was signed. Sign-off is an event that only the math-reviewer role and the user can cause, so an agent that edits a theorem cannot re-sign it.

Coordination rules from the chat history

  • No recurring AI check prompts: console-api's watchers (device, stall, repeated notices) wake an agent only when something changes.
  • Workers send results to their consumer; the lead gets ≤ 300 characters and a file path.
  • Agents cannot write console state: a strict sandbox and deny rules guard the gitignored .fw-console/, and console-api is its only writer.
  • A wait of an hour or more ends the agent with a handoff note; a script spawns a fresh one.
  • After every compaction a hook re-injects the roster, names and the lead's address.
  • One plain command per Bash call; multi-step work is a committed pnpm fw command.
  • main moves only through the lead's fw land (ff-only); any other move shows up as a violation on the user's needs-you list.
