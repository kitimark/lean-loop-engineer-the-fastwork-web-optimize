Chat forensics · 848 transcripts · 135k model requests

The agents did their work. The loop around them did not.

Reading every v1 transcript showed one overloaded lead at the centre of everything. Recurring check prompts woke it most of the time, and idle agents lost their cache and paid to rebuild it. The user ended up as device technician and status relay.

Biggest costs and problems

  • Idle agents losing their cache: 2,924 cold rewrites cost $2,763 (24%).
  • 19 agents alive over 24 hours cost 36% of all spend.
  • 57% of 5,393 errors were worktree refusals of inline shell scripts.
  • 139 of 276 incidents came from the project's own tooling and guards; 4 from agent mistakes.
  • 82–105 of 166 user console steps were device chores; one re-plug waited 11 h 41 min.

What worked and stays

  • Console steps, Try-it proposal pages and comment buttons (median 10 min to a decision).
  • Short, fresh agents: 645 agents under an hour cost only 11%.
  • Message delivery (0.35% failed) and fast replies.
  • One lander with fast-forward-only merges: 0 merge commits in 2,483.
  • A/A noise floors, pinned baselines, prediction cards before data.
The core idea

A two-speed loop

The inner loop runs on every change and never touches the phone: it counts the engine's work in Chromium and WebKit and screens the result with a proved rule. The outer loop runs in phone sessions the user books. It calibrates the cost model and licenses kinds of change to land without the device.

Measurement

Count the work, then price it

Timing changes with heat, load and the device. The amount of work an engine does in a frame does not: how many styles it recalculated, how many layouts it ran, how many pixels it repainted, how many layers it built. v2 steps the page one virtual frame at a time, reads those counts and feeds them to a cost model.

Chromium · development aid

Headless Chrome in a Linux container, because frame stepping (BeginFrameControl) is refused on macOS. The page's own clock advances; animations are never seeked, so compositor animations stay on the compositor.

style passes · elements · layouts · paint · raster rects · layers · compositeFailed

WebKit · the target

The iOS Simulator's Mobile Safari through the Web Inspector protocol. The model is calibrated on the real iPhone, because only the phone shows render-server, GPU and finger-only costs.

recalc styles · layouts · paint area · layer census · backing bytes · accelerated animations

The WebKit cost model, per frame

dt ≈ max( T_req , W + F + U + δ ) W = J + Σ c·counts F = max( s²·Ap / R_cg , Bn / R_alloc ) T_req = 16.67 ms

W is main-thread work, F the GPU raster wait, U the UI-process apply. Every coefficient is fitted on the phone and constrained to be non-negative, so removing work can never raise a prediction.

The screening rule needs no calibration

If a variant's count vector is no higher than the baseline's in every component of every frame, and lower somewhere, its predicted cost cannot be higher under any non-negative coefficients. That is a theorem in Lean. A change that passes it is "less work" and can land without the phone, provided the counted vector covers everything the change touches.

WLess work

Strictly less work in every frame, in both engines, and the same sign on the original page.

The rewrite

About 32 parts, each behind a flag

The homepage is rebuilt in React 19 as parts such as hero.countdown, people.deck and morph.tween. Every part has a faithful variant that matches the original, plus variants an experiment can switch on from the URL.

# one part swapped, both engines, the v1 scripted swipe
pnpm fw run --preset original \
  --fw hero.countdown:strip \
  --engines chromium,webkit --profile swipe-v1

# ablate every People part, one arm each
pnpm fw run --preset original --ablate 'people.*'

# in the browser
/?preset=original&fw=hero.countdown:strip

MUI everywhere, with styles compiled ahead of time

The user decided the site uses MUI throughout. Runtime CSS-in-JS would insert styles while the page scrolls and add to the very costs being measured, so the plan compiles styles to static CSS ahead of time and adds a check that fails a run if any style is inserted during the measured scroll. Which compile-time stack to use is being researched now (plan revision 4).

Lean 4.35.0 · installed

Prove the decisions that could mislead an experiment

Lean is not used for everything. It holds the few rules whose wrong answer would send an experiment the wrong way. A small compiled program, fwcore, makes those decisions for the TypeScript tools over JSON lines.

ModuleProves
FramesVsync tick math and slow-frame thresholds; no 60 vs 120 Hz mix-ups.
Verdict"Better" only when every variant run beats every control run; false-win rate exactly 1/70 for 4 vs 4.
FlagsEvery config resolves to one variant per part; an A/B pair differs in exactly one part.
Cost / screenLess work in every frame never predicts a higher cost.

A browser copy of the flag resolver is checked against Lean with 2,000 generated cases on every change. A bug ledger records which bugs proofs caught versus tests, and at milestone M4 it decides whether Lean earns its place.

Coordination rules from the chat history

  • No recurring AI check prompts: watchers wake an agent only when something changes.
  • Workers send results to their consumer; the lead gets one line and a file path.
  • A wait of an hour or more ends the agent with a handoff note; a script spawns a fresh one.
  • After every compaction a hook re-injects the roster, names and the lead's address.
  • One plain command per Bash call; multi-step work is a committed pnpm fw command.

Budget: looser, by the user's choice

The user chose speed over token savings. Hard caps become cost reports with soft alerts. The rules above stay because they make the loop faster and less error-prone, not only cheaper.

  • Full look and work parity only for experiment parts; look parity for the rest; a time box per part.
  • The parity reference is snapshot b1789284481295-a455e793; v1's best build becomes the v1-best preset.
